## Reproduce

You need Docker (with `buildx`, which Docker Desktop and current Docker Engine include), `git`
and `make`. You need no Python, no cloud account, no credentials and no `cloud.env`.

```bash
make reproduce
```

expected test_roc_auc: 0.8482 ± 0.0010

Then check it:

```bash
make verify
```

`make verify` uses the Python standard library only.

**Runtime:** about 3–4 minutes from a cold Docker cache on an Apple Silicon laptop. Most of that
is building the image and the first run under amd64 emulation. Once the image is cached, a
rerun takes about 10 seconds. A native amd64 machine is faster.

**What the command does:**
1. It builds the training image for `linux/amd64`: a digest-pinned base and a hash-locked
   `pip install --require-hashes`.
2. It generates the dataset inside that image with seed `20260101`.
3. It trains and evaluates inside the same image.
4. It writes `reports/metrics.json` and logs the run to `reports/mlflow.db`.

The output also prints the data version. Expect `data_fingerprint` = `422cccb9136e8140` and
`dvc_md5` = `1c886b512c8a5c9bf723da1cd119fc80.dir`, which is the `md5` in
[`data/raw.dvc`](data/raw.dvc).

### How the tolerance was chosen

These are measured values, not guesses:

| Comparison | Δ test ROC AUC |
|---|---|
| Same seed, two `make reproduce` runs (amd64 image) | **0** — `metrics.json` is byte-identical |
| Same seed, amd64 container vs. native arm64 macOS (same lock file) | 0.000013 |
| Same config, seed changed (5 seeds, table below) | range **0.050**, std 0.0185 |

A fixed seed reproduces to the bit on amd64. The ±0.0010 tolerance is about 75× the largest
cross-CPU drift I observed. That margin covers different CPUs picking different NumPy SIMD
kernels. It is still 50× smaller than what a seed change does, so an unset seed or different
data fails `make verify` rather than hiding inside the tolerance.

## The problem and the data

240 machines, 25 readings each, 6 sensor features, and a binary target `failed_within_7d`.
The positive rate is 11.7%. The metric is ROC AUC on a held-out test split.

**Where the data comes from:** it is synthetic, generated by
[`scripts/make_dataset.py`](scripts/make_dataset.py) from a seed. The same seed and the same
pinned NumPy give a byte-identical file: the CSV generated on arm64 macOS and the one generated
in the amd64 container are identical. It is versioned with DVC. `data/raw` is tracked by
[`data/raw.dvc`](data/raw.dvc), and the remote is `${BLOB_URI}/dvc` in Google Cloud Storage.

Machines have persistent characteristics: a hot-running machine reads hot in every row. So the
train/validation/test split (60/20/20) is **grouped by `machine_id`**, and every reading from one
machine lands in exactly one partition. The split is built inside the pipeline
([`src/data.py`](src/data.py)) and is deterministic given the seed. Two tests in
[`tests/test_data.py`](tests/test_data.py) fail if a `machine_id` or a `reading_id` appears in
more than one split.

## Tracked runs (Task 5)

Every run logs:
- hyperparameters and the seed, as params
- `val_*` and `test_*` metrics, separately
- `git_commit`
- `dvc_md5`, the DVC hash recomputed from the bytes the model actually read
- `dvc_md5_tracked`, the hash in `data/raw.dvc`, plus `data_matches_dvc`
- the fitted model, as an MLflow model artifact

`make study` reproduces the table below. It uses a local Python 3.11 environment built from
`requirements.txt`, and `MLFLOW_TRACKING_URI` from `cloud.env`.

**Study: `max_depth`, at fixed seed 20260101** (n_estimators 200, min_samples_leaf 5):

| run | max_depth | val ROC AUC | test ROC AUC |
|---|---|---|---|
| depth-3 | 3 | 0.8386 | 0.8524 |
| depth-5 | 5 | **0.8423** | **0.8530** |
| depth-8 | 8 | 0.8364 | 0.8483 |
| depth-12 | 12 | 0.8353 | 0.8425 |
| depth-16 | 16 | 0.8361 | 0.8417 |

Deeper trees overfit the 144 training machines. Validation peaks at depth 5, and test ROC AUC
falls by 0.011 from depth 5 to depth 16. The claim above stays on the default `max_depth=8`.
Moving to depth 5 is a Lab 2 decision, and it would change the claim line.

**Seed spread of the default config** (max_depth 8). This is where the tolerance comes from:

| run | seed | val ROC AUC | test ROC AUC |
|---|---|---|---|
| seed-1 | 1 | 0.8369 | 0.8729 |
| seed-2 | 2 | 0.8481 | 0.8546 |
| seed-3 | 3 | 0.8406 | 0.8405 |
| seed-4 | 4 | 0.8639 | 0.8229 |
| seed-5 | 5 | 0.8749 | 0.8437 |

All ten runs were made at commit `487cdf8` with `dvc_md5` = `1c886b512c8a5c9bf723da1cd119fc80.dir`
and `data_matches_dvc` = `True`. The seed moves the *split*, not just the forest: a different 48
test machines means a different test set, which is why the spread is so wide.

## Reproducibility trade-off

**I would drop the hashes first.** The `==` pins still fix every version, and PyPI never lets a
published file be replaced. What I lose is protection against a *new* file appearing under an
old version (a late platform wheel, or a build-tag re-release) or a tampered mirror. That is a
supply-chain gap, not an everyday reproducibility failure. The other two break silently and
often. `python:3.11-slim` was last rebuilt on 2026-09-01, and the tag follows every rebuild
without any commit from me. Dropping seeds moves the split: my seed runs swing test ROC AUC
across 0.823–0.873, fifty times my tolerance.

## Notes for the grader

- **Only Docker is needed.** `make reproduce` never runs Python on the host. It does not need
  `cloud.env`, `dvc pull` or any credential, and it takes no environment variables. Every input
  is in the repository.
- **Data:** the command regenerates the dataset inside the pinned image instead of pulling it.
  The printed `dvc_md5` should equal the `md5` in `data/raw.dvc`, and the MLflow tag
  `data_matches_dvc` records the check. The DVC remote at `${BLOB_URI}/dvc` is a private GCS
  bucket, so `dvc pull` needs `roles/storage.objectViewer` on it. `make reproduce` does not
  depend on it.
- **Container user:** the image runs as non-root `runner` (uid 10001) by default. `make reproduce`
  runs it with `--user $(id -u):$(id -g)`. On Linux, a bind mount keeps host ownership, so uid
  10001 could not write `reports/`. On Docker Desktop this difference is invisible.
- **Platform:** the image is always `linux/amd64` (`PLATFORM` in the Makefile). On Apple Silicon
  it runs under emulation, and the numbers are identical to native amd64.
- **Loose links found and fixed while doing this lab:**
  1. `make reproduce` generated the data with the *host's* Python and NumPy. It now runs inside
     the image.
  2. `predict_proba` summed per-tree probabilities in thread-completion order, so the last bits of
     each score depended on core count. Prediction is now single-threaded.
  3. The container had no `.git`, so `git_commit` logged `unknown`. The SHA is now passed in as
     `GIT_COMMIT`.
  4. The bind-mount permissions described above.
- `make teardown` still raises `NotImplementedError("Lab 5")`. The scaffold schedules the GCP
  `teardown` for Lab 5. Lab 1 creates only a bucket prefix and one image.
